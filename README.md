# Импульс

Десктопный мессенджер для Windows в духе Telegram: личные и групповые чаты, текстовые сообщения в
реальном времени через интернет, передача файлов `.txt`, фото профиля, выбор шифрования и
демонстрационное окно «Эфир» с «перехватом» сообщений.

Клиент — Electron + React + TypeScript (electron-vite). Сервер — Node.js + Express + WebSocket +
встроенный `node:sqlite`. Есть также Android-оболочка на Capacitor (`mobile/`) с тем же
интерфейсом и сборкой в APK/AAB.

Дополнительно встроена **прямая P2P-связь без аккаунта**: Windows и Android соединяются через
WebRTC/STUN, при строгом CGNAT автоматически переключаются на зашифрованный WebSocket-relay,
а при недоступном signaling обмениваются офлайн-кодами вручную. Тексты и файлы шифруются на
устройствах (ECDH P-256 + AES-256-GCM), сервер видит только шифротекст.

## Возможности

- Вход по номеру телефона: простая капча и код из SMS. В dev-режиме код печатается в терминале
  сервера, в `server/data/sms.log` и показывается на экране ввода кода при локальном запросе;
  никнейм и фото профиля меняются в настройках. Фото выбирается из файлов/галереи, обрезается
  по центру и сжимается до 256×256. В production коды не пишутся в лог: без `SMS_DEV_MODE=1`
  запрос возвращает 503, пока не подключён реальный SMS-провайдер.
- Личные чаты: поиск пользователя по точному номеру телефона, история переписки. Полный
  справочник пользователей не отдаётся — поиск по нику и выгрузка всех номеров отключены,
  а точный поиск ограничен 30 запросами в минуту. Если номера ещё нет в Импульсе, создаётся
  аккаунт-приглашение с номером вместо имени; после
  первого входа по SMS он превращается в обычный аккаунт, а чат и история сохраняются.
- Перенос аккаунта на другое устройство: на новом устройстве выберите «Войти с другого
  устройства», введите номер и 8-значный код из чата «Импульс · Безопасность» на старом
  устройстве. После ввода кода старое устройство показывает подтверждение «Передать ключ» —
  без этого клика ключ не уходит. Затем ключ сложного шифрования передаётся напрямую между
  устройствами по одноразовому ECDH-каналу, после завершения старая сессия отзывается. Сервер
  видит только открытые ECDH-ключи и шифротекст, а не сам E2EE-ключ (при честном сервере;
  вредоносный сервер может подменить ключ, поэтому сверяйте отпечаток). Если старое устройство
  недоступно, можно войти без старой истории, но только после подтверждения номера кодом из
  SMS — одного украденного токена для сброса ключа недостаточно.
- Группы: название, выбор участников из списка пользователей, отображение имён отправителей,
  список участников в карточке группы и общий для всех режим шифрования. Менять режим может
  создатель группы; после его выхода управление переходит следующему участнику.
- Сообщения в реальном времени (WebSocket), статусы «в сети», «печатает…», отметки о прочтении.
- Статусы сообщений: **часы** — сообщение сохранено локально и ждёт интернета; **одна галочка** —
  дошло до сервера; **две серые галочки** — получено собеседником; **две зелёные** — прочитано.
  В группе доставка и прочтение подтверждаются всеми остальными участниками. Очередь отправки
  хранится локально и переживает перезапуск приложения.
- Удаление своих сообщений: плавная анимация, у собеседника сообщение исчезает синхронно.
  Удалить можно правой кнопкой мыши по сообщению → «Удалить сообщение».
- Редактирование своих сообщений и ответы: правой кнопкой по сообщению → «Редактировать» или
  «Ответить». У изменённых сообщений появляется пометка «изменено»; ответ показывает, на какое
  сообщение он отправлен, и позволяет перейти к оригиналу.
- Трей: «Импульс» можно сворачивать в системный трей при закрытии и запускать свёрнутым;
  открыть обратно — по значку. Меню трея: открыть, окно «Эфир», выход.
- Звуки: свой звук, громкость и отдельное включение для каждого события — входящие/исходящие
  сообщения, ответы, редактирование, удаление, файлы, «печатает…», online/offline, доставка,
  прочтение, открытие чата, клики интерфейса, карточки «Эфира». Можно загрузить свои MP3/WAV/OGG.
- Язык интерфейса: русский и English (beta). Английский переводит основные экраны; часть
  служебных и динамических сообщений может остаться на русском.
- Очистка истории: правая кнопка мыши по чату в списке → «Очистить историю». История исчезает
  только у вас, чат остаётся в списке. Удаление личного чата тоже скрывает его **только у вас**:
  у собеседника переписка и чат сохраняются. Выйти из группы можно через «Покинуть группу» или
  «Покинуть тихо»; группа удаляется, когда её покидает последний участник.
- Удаление аккаунта: **Настройки → Удаление аккаунта**. Удаляются профиль, личные чаты, сообщения
  и файлы в группах, телеметрия и бэкапы; старые токены перестают работать. Для Google Play
  доступна веб-страница `https://<сервер>/delete-account`.
- Прокручиваемая история и закреплённое закруглённое поле ввода: шапка чата и настройки
  остаются на месте при длинной переписке.
- Файлы только `.txt`, размером до 1 ГБ (загрузка с прогрессом, скачивание с прогрессом).
- Шифрование на выбор для каждого чата: **Лёгкое**, **Сложное** или **без шифрования**; при
  смене режима в чат добавляется системное сообщение. У каждого режима есть кнопка «i» с краткой
  справкой — без дублирования описаний в интерфейсе. Служебный код «Лёгкого» нигде не показывается.
- Окно **«Эфир»** (включается в настройках): сообщения «летят» по экрану. При выключенном
  шифровании виден текст, при включённом — только base64-шифротекст. «Лёгкое» можно
  **взломать прямо в окне**: «Эфир» реально перебирает 4-символьные ключи (старые
  3-символьные сообщения тоже поддерживаются). Новые light-v5 сообщения имеют свой код и ключ
  на каждое сообщение; после взлома ключ помечается удалённым, а само сообщение остаётся. Доступны режимы
  «Взломать на CPU» и «Взломать на GPU» (WebGPU, например GTX 1650). «Сложное» в демо не
  взламывается.
- Автозапуск при входе в Windows (включается в настройках). Если окно «Эфир» включено,
  при запуске открываются оба окна — основное и «Эфир».
- Телеметрия устройства: при входе десктопный клиент отправляет на сервер модель процессора,
  число логических ядер, архитектуру, версию приложения и объём ОЗУ. Данные видны в настройках
  и хранятся в профиле пользователя.
- Резервное копирование **по умолчанию выключено**. При включении сервер раз в сутки сохраняет
  JSON-снимок переписки (хранятся 7 последних), плюс доступна кнопка «Скачать бэкап». Папку для
  ручных бэкапов можно выбрать в настройках.
- Четыре темы оформления, галерея фонов и свой фон отдельно для переписки и окна «Эфир» с
  настройкой прозрачности, кастомный заголовок окна, трей-подобное окно «Эфир» без рамки, режим
  «поверх всех окон».
- **Прямая P2P-связь**: личный зашифрованный чат между двумя устройствами без регистрации,
  WebRTC DataChannel, relay-резерв, офлайн-коды, очередь сообщений и статусы доставки.

## Прямая P2P-связь (без аккаунта)

Кнопка **P2P** в правом нижнем углу открывает отдельный канал, не связанный с аккаунтами и
историей серверных чатов. Он нужен, когда сервер за localtunnel недоступен, когда не хочется
регистрироваться или когда мобильный оператор даёт строгий CGNAT.

### Как соединить Windows и Android

**Онлайн-код (обычный путь):**

1. На Windows откройте **P2P → Создать приглашение**. Клиент создаст WebRTC offer, ECDH-ключи
   и 10-символьный код.
2. На Android откройте **P2P → Онлайн-код**, введите код и нажмите **Подключиться**.
3. В шапке появится **P2P Direct** (прямой UDP), **TURN Relay** (если настроен TURN) или
   **Relay Fallback** (WebSocket через сервер). Сверьте 6-значный код на обоих экранах.

**Офлайн-обмен (если signaling-сервер недоступен):**

1. Windows: **P2P → Офлайн-обмен → Я приглашаю**, скопируйте `IMPULSE-OFFER1:…`.
2. Android: вставьте код в **«У меня есть код приглашения»** и получите `IMPULSE-ANSWER1:…`.
3. Перешлите ответ обратно на Windows, вставьте в поле ответа и нажмите **Завершить соединение**.
   Прямой WebRTC-канал поднимется без какого-либо сервера.

### Сетевой pipeline

1. **WebRTC/STUN first.** Используются бесплатные STUN `stun.l.google.com:19302` и
   `stun.cloudflare.com:3478`; ICE сам пробивает NAT и выбирает host/srflx-пару. Это работает
   и на мобильном интернете, если оператор не блокирует UDP.
2. **UPnP / NAT-PMP.** На Windows при первом открытии P2P панель пытается пробросить локальный
   порт сервера через домашний роутер и показывает прямой адрес, если внешний IP публичный.
   В CGNAT или при выключенном UPnP попытка безопасно пропускается. Сам WebRTC в пробросе не
   нуждается — ICE использует STUN; UPnP здесь ускоряет доступ к локальному серверу.
3. **Optional TURN.** Если у вас есть бесплатный/свой TURN, задайте `VITE_TURN_URLS`,
   `VITE_TURN_USERNAME`, `VITE_TURN_CREDENTIAL` при сборке. Без TURN симметричный CGNAT
   уходит на следующий шаг.
4. **WebSocket relay fallback.** Тот же сервер принимает только непрозрачные AES-GCM конверты:
   `POST /api/p2p/...` для signaling и `/p2p-relay` для мгновенной доставки. Если доступен
   только HTTPS, клиент автоматически использует HTTP-очередь событий.
5. **Manual SDP.** Если недоступны и signaling, и relay, два устройства обмениваются полными
   SDP-кодами через любой другой канал.

### Шифрование и доставка

- Каждая сессия создаёт одноразовую пару ECDH P-256. Общий ключ выводится через HKDF-SHA-256,
  каждое сообщение/файловый чанк шифруется AES-256-GCM со случайным nonce и AAD.
- 6-значный SAS-код строится из обоих публичных ключей и соли. Его нужно сверять голосом или
  другим каналом: signaling-сервер не должен подменить ключи незаметно.
- Исходящая очередь хранится в `localStorage` и переживает обрыв LTE/Wi-Fi. Повторная отправка
  использует стабильный `messageId`, поэтому дубликаты отсекаются на получателе. Статусы:
  `queued` (часы), `sent` (одна галочка), `delivered` (две галочки).
- Файлы до 40 МБ передаются чанками по 24 КБ; каждый чанк шифруется отдельно. Получатель
  собирает Blob и может скачать его до перезапуска приложения (после перезапуска остаются имя,
  размер и статус, но не содержимое).
- История прямой связи хранится локально по паре устройств. Сервер не сохраняет ни тексты,
  ни файлы; relay-события живут в памяти и удаляются вместе с комнатой (TTL 12 часов).

> Прямая связь не заменяет серверные чаты: у неё нет поиска по аккаунтам, групп и серверной
> истории. Это отдельный канал «устройство ↔ устройство».

## Безопасность

Подробная модель угроз и чек-лист — в [SECURITY.md](SECURITY.md). Кратко:

- JWT-сессии отзываются через `POST /api/auth/logout`; на desktop токен
  хранится в зашифрованном виде через `safeStorage`, а WebSocket использует
  одноразовый билет вместо токена в URL.
- CORS и WebSocket проверяют Origin: сторонние сайты не могут обращаться к
  локальному серверу, даже если он запущен в dev-режиме.
- Публичные ключи собеседников запоминаются; при изменении ключа появляется
  предупреждение, а отправка «Сложных» сообщений блокируется до подтверждения
  «Я сверил».
- Вход без старой истории требует SMS-кода на номер аккаунта: одного
  украденного токена недостаточно, чтобы сбросить E2EE-ключ.
- Действуют лимиты на сообщения, чаты, загрузки, капчу и WebSocket-соединения;
  для файлов есть отдельная квота `MAX_USER_STORAGE`.
- В группах участникам не отдаются номера телефонов других участников: телефон
  виден только в личном чате и в своём профиле.
- Главный процесс Electron работает с `sandbox: true` и проверяет IPC-запросы:
  ключи другого аккаунта, произвольные URL загрузки и папки бэкапов отклоняются.

> Абсолютную безопасность гарантировать нельзя: вредоносный сервер, SIM-swap,
> компрометация устройства, отсутствие forward secrecy и демо-режимы
> «Лёгкое»/«Без шифрования» остаются вне гарантий. См. ограничения ниже.

> **Важно:** «Лёгкое» и «Без шифрования» — демонстрационные режимы: сервер знает ключ чата.
> «Сложное» для **новых текстовых** сообщений — E2EE (RSA-OAEP + AES-256-GCM), но без forward
> secrecy. Старые complex-сообщения, файлы и «Лёгкое» не являются E2E. Подробнее — в разделе
> «Шифрование».

## Требования

- **Node.js 24+** (используется встроенный модуль `node:sqlite`, нативный сборщик не нужен).
- Windows 10/11 для клиента.
- Для продакшена: VPS с Docker и доменом (для HTTPS/WSS).

## Локальный запуск

```powershell
npm install           # корневые dev-зависимости, включая localtunnel
npm run install:all   # установка зависимостей сервера и клиента
npm run dev           # сервер + клиент одновременно
```

Или по отдельности:

```powershell
npm run dev:server    # http://localhost:3000
npm run dev:desktop   # Electron-клиент (Vite dev-сервер на 5173)
```

Сервер при старте печатает локальный адрес; по умолчанию он слушает только
`127.0.0.1`, поэтому доступен лишь с этого компьютера. Для второго компьютера
или реального Android-телефона в той же сети задайте `HOST=0.0.0.0` и
перезапустите сервер — тогда в консоли появятся сетевые адреса вида
`http://192.168.1.10:3000`. Без этой настройки сервер недоступен по LAN.
Для связи через localtunnel `HOST=0.0.0.0` не требуется: туннель подключается
к loopback. P2P-панель работает даже без запущенного сервера.

### Сетевая конфигурация

Все Windows-скрипты читают значения из `network-config.ps1`, поэтому порт и
поддомен больше не расходятся между сервером, туннелем и watchdog:

```powershell
$env:IMPULSE_PORT = '3000'                 # по умолчанию 3000
$env:IMPULSE_SUBDOMAIN = 'moy-server-2026' # ваш стабильный *.loca.lt
```

Адрес сервера нормализуется единообразно в main-процессе и renderer:

- публичный хост без схемы получает `https://`, локальный/частный — `http://`;
- `ws://`/`wss://` автоматически переводятся в `http://`/`https://`;
- принимается только origin; `/health` и `/ws` отбрасываются, произвольный путь,
  query, hash и логин/пароль отклоняются;
- health-check требует `{ "ok": true, "service": "impulse" }`, поэтому HTML-заглушка
  localtunnel или чужой сервис не считаются рабочим сервером;
- Android-сборка по умолчанию использует `https://moy-server-2026.loca.lt`
  (переопределяется `VITE_SERVER_URL` при сборке или на экране входа).

WebSocket переподключается с экспоненциальным backoff и jitter, проверяет
зависший handshake и «полуживое» соединение по pong, а также сразу реагирует на
`online` и возврат Android-приложения на передний план. Очередь отправки
привязана к origin сервера, сохраняется между перезапусками и учитывает
`Retry-After` при 429/5xx.

### После перезагрузки компьютера

Сервер и клиент — разные процессы: без запущенного сервера приложение не сможет войти и
покажет ошибку подключения. Порядок действий:

1. Откройте папку проекта.
2. Дважды щёлкните **`start-impulse.cmd`** — скрипт запустит сервер (если он ещё не запущен) и
   откроет клиент.
3. Если клиент не появился, запустите **`start-server.cmd`**, дождитесь строки
   «Импульс — сервер запущен», затем откройте приложение вручную.
4. Для телефона на мобильном интернете запустите **`start-tunnel.cmd`** (сервер должен быть
   уже запущен). Скрипт проверит локальный `/health`, поднимет localtunnel и watchdog, затем
   выведет `https://moy-server-2026.loca.lt`. Остановка — **`stop-tunnel.cmd`**.

`start-server.cmd` использует Node.js, встроенный в Electron, поэтому отдельно устанавливать
Node.js не нужно. Для localtunnel нужен Node.js или Electron из зависимостей проекта —
`start-tunnel.ps1` выбирает доступный вариант автоматически. Сервер работает в отдельном
свёрнутом окне консоли; чтобы остановить его, закройте это окно на панели задач. Данные сервера
лежат в `server/data`, файлы — в `server/uploads`.

Если нужно, чтобы после входа в Windows автоматически поднимались и сервер, и клиент, положите
ярлык на `start-impulse.cmd` в папку автозагрузки: нажмите `Win+R`, введите `shell:startup` и
скопируйте туда ярлык. Настройка автозапуска внутри приложения запускает только клиент — сервер
при этом должен быть уже запущен.

### Как проверить вдвоём на одном компьютере

1. Зарегистрируйте первого пользователя в приложении: номер, капча, код из SMS и никнейм.
   Код появляется в терминале сервера и в `server/data/sms.log`.
2. Второго пользователя откройте в браузере на другом origin: например, первое окно —
   `http://localhost:5173`, второе — `http://192.168.0.10:5173` (подставьте локальный IP
   компьютера). Это разные origin, поэтому сессии в localStorage не пересекаются. В браузере
   работает весь интерфейс, кроме системного диалога сохранения файла и отдельного окна «Эфир»:
   файл скачивается обычным способом, а «Эфир» можно открыть по адресу `http://localhost:5173/#air`.
3. Либо установите приложение на второй компьютер (или запустите второго пользователя в другом
   профиле Windows) и подключите его к тому же серверу.
4. В поиске нажмите «+», введите номер второго пользователя и начните чат. Если второго номера
   ещё нет в базе, появится аккаунт-приглашение с номером вместо имени.

> Два окна установленного приложения на одном компьютере используют один профиль и одну сессию —
> для двух разных аккаунтов на одной машине удобнее вариант с браузером и разными origin.

## Два пользователя через интернет

### Вариант 1: localtunnel (бесплатно, без VPS)

1. На Windows запустите `start-impulse.cmd` (сервер + клиент), затем `start-tunnel.cmd`.
   Дождитесь `Туннель работает: https://moy-server-2026.loca.lt`.
2. На Android установите APK. Адрес по умолчанию уже равен
   `https://moy-server-2026.loca.lt`; если поддомен другой — нажмите «Изменить» на экране входа
   и введите свой `https://…loca.lt`.
3. Зарегистрируйте два аккаунта. Код SMS в dev-режиме смотрите в консоли сервера или
   `server/data/sms.log`: через localtunnel `devCode` намеренно **не возвращается** клиенту.
4. Найдите второго пользователя по номеру через «+» и пишите.

Если localtunnel недоступен или мобильный оператор режет соединение, используйте кнопку **P2P**:
прямой WebRTC-канал не зависит от localtunnel, а при строгом CGNAT уйдёт в relay. Для полностью
автономного соединения используйте офлайн-обмен SDP-кодами.

> localtunnel — бесплатный демо-транспорт: возможны ограничения скорости, засыпание и чужая
> занятость поддомена. Watchdog перезапускает процесс, но не делает localtunnel production-SLA.

### Вариант 2: VPS с HTTPS

1. Разместите сервер на VPS (см. «Развёртывание») и получите HTTPS-адрес, например
   `https://chat.example.ru`.
2. Установите клиент «Импульс» на оба компьютера.
3. На экране входа нажмите «Изменить» рядом с адресом сервера, введите `https://chat.example.ru`,
   нажмите «Проверить» (появится зелёная точка) — адрес сохранится.
4. Зарегистрируйте два аккаунта (разные номера телефонов). Код из SMS появится в терминале
   сервера и в `server/data/sms.log`, только если сервер запущен в dev-режиме или с
   `SMS_DEV_MODE=1`. В production без этого флага запрос вернёт 503, а код в лог не попадёт:
   для реальной отправки нужен SMS-провайдер.
5. Один пользователь находит второго по номеру через «+» и пишет сообщение. Если номер ещё не
   зарегистрирован, создаётся аккаунт-приглашение; после входа по SMS он станет обычным, а история
   чата сохранится.

## Шифрование

Режим задаётся для каждого чата отдельно (карточка чата → «О чате») и по умолчанию для новых чатов
(настройки). Названия уровней — бытовые, без алгоритмов:

| Режим | Что происходит | Что видит сервер |
| --- | --- | --- |
| Лёгкое | AES-256-GCM. Новые light-v5 сообщения: 4-символьный код и 32-байтовый ключ зависят от `nonce` сообщения. Старые light-v2/v3: код и ключ выводятся из ключа чата | ключ чата (и `nonce` для v5), поэтому сервер может расшифровать текст |
| Сложное | новые текстовые сообщения: одноразовый AES-256-GCM content key; для каждого участника он заворачивается в RSA-OAEP-2048 | шифротекст и `keyEnvelopes`; content key серверу не передаётся |
| Без шифрования | текст хранится и передаётся открытым | открытый текст |

Форматы сообщений:

- **Сложное v3 (E2EE):** `content = base64(ciphertext || GCM-tag)`, `nonce = base64(12 байт)`,
  `keyEnvelopes[userId] = base64(RSA-OAEP(contentKey))`. Приватный RSA-ключ создаётся на
  устройстве, публичный хранится на сервере. В карточке чата показывается отпечаток публичных
  ключей — его можно сверить с собеседником по другому каналу.
- **Лёгкое v5:** `code = base62(SHA-256("impulse-light-code-v2:chatKey:chatId:nonce"))` — 4 символа;
  `content = base64(AES-GCM(deriveLightKey(chatId, nonce, code)) || tag)`. У каждого сообщения
  свой `nonce`, поэтому свой код, ключ и позиция в пространстве `62⁴ = 14 776 336`. После
  успешного взлома ключ помечается удалённым, а сообщение остаётся в чате.
- **Лёгкое v2/v3 (старые):** 3- или 4-символьный код и ключ выводятся из ключа чата; у сообщений
  одного чата они одинаковые. Пространство перебора — `62³ = 238 328` или `62⁴ = 14 776 336`.
  «Эфир» перебирает и старые, и новые сообщения.
- **Старые форматы:** light v1 (XOR), complex v1 и режимы «Простое»/«Надёжное» поддерживаются
  для чтения. При старте сервера старые light-сообщения один раз переводятся в light v2, а
  legacy-режимы — в complex v1 с ключом чата. Поэтому история не пропадает, но старые
  complex-сообщения остаются не E2E.

Что важно понимать:

- «Сложное» E2E действует только на **новые текстовые** сообщения. Файлы `.txt` в этом режиме
  не отправляются; в «Лёгком» и «Без шифрования» они лежат на сервере открытыми.
- Ключ чата по-прежнему хранится на сервере (в зашифрованном мастер-ключом виде). Он нужен для
  «Лёгкого» и старых сообщений, поэтому сервер технически может их прочитать.
- Forward secrecy нет: если приватный RSA-ключ устройства скомпрометирован, старые complex-сообщения
  можно расшифровать. Один ключ соответствует одному аккаунту; при переносе он копируется на новое
  устройство.
- Сервер раздаёт публичные ключи участников. Отпечаток в карточке чата помогает заметить подмену,
  но автоматической проверки ключей и key transparency пока нет. Клиент запоминает отпечатки: при
  изменении ключа собеседника появляется предупреждение, а отправка «Сложных» сообщений
  блокируется до нажатия «Я сверил». Вредоносный сервер всё равно может подменить ключ при первом
  обмене или при переносе устройства — сверяйте отпечаток по другому каналу.
- Старые названия (`aes-256-gcm`, `chacha20-poly1305`) принимаются как «Сложное»; сообщения
  прежних режимов «Простое» и «Надёжное» один раз перешифровываются при старте сервера.

Смена режима рассылает системное сообщение обоим участникам («Шифрование включено: Сложное»). Если
сообщение не отправилось из-за смены режима (HTTP 409 `ENCRYPTION_MODE_CHANGED`), клиент предложит
повторить отправку — оно будет перешифровано под актуальный режим. Переключить чат в «Сложное»
можно только когда у всех участников есть опубликованный ключ устройства.

## Окно «Эфир»

Включается в настройках: **Настройки → Окно «Эфир» → Перехват сообщений (демо)**. Открывается
отдельное окно без рамки, в котором карточки сообщений летят справа налево по «полосам».
Если настройка включена, при запуске приложения окно «Эфир» открывается автоматически вместе с
основным.

- открытый текст — зелёная карточка с содержимым;
- шифрование — жёлтая карточка с моноширинным base64-шифротекстом, меткой уровня и оценкой взлома
  (`Взлом: реальный перебор 14 776 336 ключей`, `238 328` для старых или `Взлом: невозможен`);
- **взлом**: у «Лёгкого» есть два режима — **CPU** и **GPU**. Карточка закрепляется в центре и
  показывает настоящий перебор: прогресс, число проверенных ключей, время и кнопку остановки.
  Каждый кандидат — это 4 символа из `A-Z a-z 0-9` (для старых сообщений — 3); из него выводится
  AES-256-ключ (в light-v5 — с учётом `nonce` сообщения), которым расшифровывается реальный
  шифротекст. Совпадение GCM-тега означает, что ключ найден. Сам подобранный код в интерфейсе не
  показывается. После успешного взлома ключ помечается удалённым: сообщение остаётся в истории
  и бэкапе, но повторный перебор в «Эфире» для него недоступен. Статус показывается в футере.
  Никакого запроса ключа у сервера и никакого таймера — только перебор;
- перебор на CPU идёт в **Web Workers по всем логическим ядрам**. Ползунок «Загрузка процессора»
  задаёт 1–95%: каждый поток работает короткими отрезками и спит пропорционально остатку, поэтому
  даже при 95% главный поток и анимация не блокируются;
- **GPU-режим** использует WebGPU compute: SHA-256, AES-256 и GHASH для проверки GCM-тега
  выполняются в WGSL на видеокарте. Панель GPU минимальная: модель адаптера, число CUDA-ядер
  (для известных моделей, например **896 у GTX 1650**) и ползунок «Загрузка GPU» 5–100%. Работа
  идёт батчами с паузами, чтобы удерживать заданный процент. Если WebGPU или аппаратный адаптер
  недоступен, режим GPU отключается;
- **«Расширенные параметры»** относятся к CPU: скорость обновления графика и счётчиков
  (100–2000 мс), живой график средней частоты CPU (WMI `ActualFrequency`; если WMI недоступен —
  базовая частота) и два счётчика — «Время ЦПУ» и «Время задачи». Время ЦПУ накапливается на
  каждом тике по формуле
  `dt * активные_потоки * (загрузка / 100) * (частота_с_графика / базовая_частота)`;
- при отмене взлома карточка не начинает путь заново, а продолжает лететь из центра влево;
- при открытии окна старые сообщения не воспроизводятся: показываются только новые, пришедшие
  после запуска «Эфира»;
- кнопки окна: пауза, «поверх всех окон», свернуть, закрыть;
- показываются только чаты текущего пользователя (без скрытой слежки за другими);
- при закрытии окна настройка автоматически выключается.

> Взлом настоящий, но сама слабость — намеренная: код выводится из ключа чата (для старых
> сообщений) или из ключа чата и nonce (для light-v5), а ключ чата хранит сервер (см. раздел
> «Шифрование»), поэтому «Лёгкое» не является E2E. Зато перебор не имитация: окно «Эфир»
> перебирает все `62⁴ = 14 776 336` кодов (или `62³` для старых), расшифровывает реальный
> AES-256-GCM-шифротекст и останавливается, когда сходится тег. На CPU 4-символьный перебор
> занимает десятки секунд, на GPU (например, GTX 1650) — обычно несколько секунд.
>
> В light-v5 код и ключ привязаны к `nonce` конкретного сообщения, поэтому у разных сообщений
> разные коды и позиции. В старых v2–v4 код общий для чата: у таких сообщений одного чата позиция
> одинаковая — это не залипший счётчик. После взлома ключ помечается удалённым, сообщение остаётся.

## Телеметрия

При входе в десктопный клиент приложение один раз собирает сведения об устройстве и отправляет их
на авторизованный эндпоинт `POST /api/telemetry`:

- модель процессора;
- число логических ядер;
- архитектура и платформа;
- версия приложения;
- номинальная частота ЦП;
- общий объём ОЗУ.

Сервер сохраняет последние значения в таблице `telemetry` (SQLite), привязанной к пользователю;
повторный вход обновляет запись. В настройках клиента отображаются модель процессора и параметры
устройства. Это именно разовый снимок при входе, а не постоянный мониторинг: данные не влияют на
шифрование и не передаются третьим лицам. В браузере модель процессора недоступна, поэтому
телеметрия отправляется только из Electron-клиента.

## Файлы и бэкапы

- Принимаются только файлы с расширением `.txt`; лимит — 1 ГБ (настраивается `MAX_FILE_SIZE`).
- Файлы лежат в `server/uploads`, доступны только участникам чата по авторизованному запросу.
- В десктопном клиенте скачанный файл автоматически сохраняется в `C:\Downloads` (папка создаётся
  при необходимости), диалог сохранения не показывается. Если файл с таким именем уже есть,
  добавляется `(1)`, `(2)` и т.д. В браузере используется стандартная папка загрузок.
- Бэкап выключен по умолчанию. При включении сервер сохраняет снимки в
  `server/data/backups/<userId>/` (7 последних) раз в сутки и сразу после включения.
- «Скачать бэкап» отдаёт JSON (файлы не включаются). В бэкап попадают только видимые чаты и
  сообщения после последней очистки истории; служебный чат «Импульс · Безопасность» исключён.
  Тексты «Лёгкого» и старых режимов сервер расшифровывает; сообщения «Сложного» v3 остаются
  шифротекстом и содержат `nonce` и `keyEnvelope` получателя — их можно расшифровать только
  закрытым ключом этого устройства.
- В десктопном клиенте ручной бэкап сохраняется в папку, выбранную в
  **Настройки → Резервное копирование → Папка для ручных бэкапов**. По умолчанию используется
  `C:\Downloads`; при совпадении имён добавляется `(1)`, `(2)` и т.д. В браузере файл попадает в
  стандартную папку загрузок.
- Бэкапы могут содержать открытые тексты — защищайте каталог `data`, файл `data/.master-key` и
  выбранную папку.

## Развёртывание на VPS (Docker + HTTPS)

1. Направьте A-запись домена (например, `chat.example.ru`) на IP сервера.
2. Установите Docker и Docker Compose.
3. Скопируйте проект на сервер и создайте `.env`:

   ```bash
   cp .env.example .env
   ```

   Заполните `IMPULSE_DOMAIN` и сгенерируйте секреты:

   ```bash
   openssl rand -base64 48   # JWT_SECRET
   openssl rand -base64 32   # MASTER_KEY
   ```

   Если оставить `MASTER_KEY` пустым, сервер создаст `data/.master-key` при первом запуске.
   Этот файл и каталог `data` нужно бэкапить вместе — без них ключи чатов не восстановить.

   Для демонстрационного сервера без SMS-провайдера добавьте в `.env` строку
   `SMS_DEV_MODE=1`: код будет писаться в `sms.log` (и в `docker compose logs`), а в клиенте
   показываться только при прямом локальном запросе. В production этот флаг лучше не включать —
   без него запросы кода возвращают 503. Каталоги `./data` и `./uploads`, создаваемые Docker
   Compose, уже исключены из git.

   Для production также задайте `CORS_ORIGINS` (список доменов через запятую, без `*`) и
   при необходимости `MAX_USER_STORAGE`. В Docker `HOST=0.0.0.0` уже задан, чтобы Caddy мог
   достучаться до контейнера; наружу публикуются только порты 80/443.

4. Запустите:

   ```bash
   docker compose up -d --build
   ```

5. Caddy автоматически получит сертификат Let's Encrypt и проксирует HTTP/WebSocket на сервер.
   Открыты только порты 80 и 443, сам Node-сервер наружу не публикуется.
6. Проверьте `https://chat.example.ru/health` → `{"ok":true}`.
7. В клиенте укажите этот адрес на экране входа.

Данные сохраняются в `./data` и `./uploads` рядом с `docker-compose.yml` — их нужно бэкапить
средствами сервера.

### Быстрый тест без VPS (cloudflared)

```bash
cloudflared tunnel --url http://localhost:3000
```

Утилита выдаст HTTPS-адрес вида `https://random-words.trycloudflare.com` — его можно указать в
клиенте. Туннель подходит для проверки, но не для постоянной работы (ограничения бесплатного
тарифа, в том числе на размер загрузок).


Результат в `desktop/release`:

## Android

Android-клиент — Capacitor-оболочка вокруг того же React-интерфейса. Проект лежит в `mobile/`,
исходники Android — в `mobile/android`, готовые файлы — в `mobile/release`.

```powershell
npm run build:android          # debug APK, разрешён HTTP для локального сервера
npm run build:android:release  # подписанные release APK и AAB
```

> После обновления сервера обязательно пересоберите Android-клиент: старые
> APK/AAB используют JWT в URL WebSocket и будут отклонены.

Для release нужны JDK 21 и Android SDK 36. На этой машине они установлены в
`%LOCALAPPDATA%\Android\openjdk\jdk-21` и `%LOCALAPPDATA%\Android\Sdk`;
`mobile/scripts/gradle.cmd` находит их автоматически. Подробности — в `mobile/README.md`.

- На реальном телефоне по умолчанию используется `https://moy-server-2026.loca.lt`. Адрес можно
  изменить на экране входа или задать `VITE_SERVER_URL` при сборке:
  `$env:VITE_SERVER_URL='https://chat.example.ru'; npm run build:android`.
  Для эмулятора вручную укажите `http://10.0.2.2:3000` (debug).
- Debug-сборка разрешает HTTP/WS для локальной сети. Release работает только с HTTPS/WSS
  (`androidScheme: 'http'` оставлен для secure-context WebCrypto в WebView). Прямой P2P-режим
  не требует HTTPS и может соединяться по офлайн-кодам даже без сервера.
- WebRTC DataChannel, WebCrypto и relay WebSocket работают в Android WebView; отдельных
  разрешений, кроме `INTERNET`, не требуется.
- Release подписывается ключом `mobile/android/keystore/impulse-release.jks`; пароль и alias
  лежат в `mobile/android/keystore.properties`. Эти файлы исключены из git, их нужно сохранить:
  без ключа Play не даст выпускать обновления.
- В Android-сборке нет окна «Эфир», автозапуска Windows и системного выбора папки для бэкапов.
- Перенос аккаунта работает и в Android, но E2EE-ключ там хранится в `localStorage` WebView, а
  старое устройство должно быть онлайн, чтобы передать ключ.
- SMS в Android-демо: сервер возвращает `devCode`, приложение показывает его на экране ввода.
  В production (`NODE_ENV=production` без `SMS_DEV_MODE=1`) нужен реальный SMS-провайдер.
- Публичная страница удаления аккаунта: `https://<сервер>/delete-account`.

## Сборка Windows и Android в GitHub Actions

В репозитории есть готовый workflow `.github/workflows/build.yml`. Он запускается по
`workflow_dispatch`, при push в `main`/`master` и по тегам `v*`, собирает две независимые задачи:

- **Windows EXE** — NSIS-установщик и portable-EXE в артефакте `impulse-windows`;
- **Android APK** — подписанный debug-ключом installable APK в артефакте `impulse-android-apk`.

1. Загрузите проект в GitHub.
2. При необходимости создайте Actions Variable `VITE_SERVER_URL` с публичным HTTPS-адресом
   (по умолчанию workflow использует `https://moy-server-2026.loca.lt`).
3. Откройте **Actions → Build Windows and Android → Run workflow**.
4. Скачайте артефакты внизу страницы запуска. В каждом лежит `SHA256SUMS.txt`.
5. Windows: распакуйте `impulse-windows`, запустите `Импульс Setup …exe` или portable-EXE.
   Android: скачайте `impulse-android-apk`, разрешите установку из неизвестных источников,
   установите APK.

Debug APK подписан debug-ключом и подходит для установки и тестирования. Для Google Play нужен
release-keystore; локальная команда `npm run build:android:release` использует
`mobile/android/keystore.properties` (файлы keystore в git не попадают).

## Готовые установщики

Для раздачи используются копии в `installers`:

- `Импульс-1.1.0-beta-windows-setup.exe` — установщик Windows;
- `Импульс-1.1.0-beta-portable.exe` — переносная версия для Windows;

Оригиналы остаются в `desktop/release` и `mobile/release` (там же лежит AAB для Google Play).

## Сброс демо-данных

Остановите сервер, удалите каталоги `server/data` и `server/uploads` и запустите сервер снова —
база, аккаунты, сообщения, файлы и бэкапы будут созданы заново. При запуске через Docker Compose
те же данные лежат в `./data` и `./uploads` в корне проекта.

## Ограничения демо-версии

- SMS не отправляются реально: в dev-режиме и при `SMS_DEV_MODE=1` код пишется в лог и
  показывается в клиенте **только при локальном запросе** (loopback). С другого компьютера
  или телефона код нужно смотреть в консоли сервера/`server/data/sms.log`. В production без
  этого флага сервер возвращает 503 и **не пишет код в лог**; для реальной отправки нужен
  SMS-провайдер, которого в проекте пока нет.
- Вход без старой истории требует SMS-кода на номер аккаунта. Если SMS-провайдер не подключён
  (production без `SMS_DEV_MODE`), этот путь недоступен — это осознанный компромисс в пользу
  безопасности.
- «Выйти» отзывает все JWT аккаунта (`auth_version`), поэтому после выхода старые сессии
  перестают работать. Мультиустройства с независимыми сессиями в проекте нет.
- Подробная модель угроз, чек-лист и остаточные риски — в [SECURITY.md](SECURITY.md).
- В серверных чатах E2E есть только у новых текстовых сообщений «Сложного» режима. «Лёгкое»,
  «Без шифрования», старые complex-сообщения и файлы сервер может прочитать. В отдельном
  P2P-канале все тексты и файловые чанки всегда шифруются ECDH/AES-GCM. Forward secrecy серверных
  complex-сообщений нет; в P2P ключи одноразовые для сессии, но SAS/отпечаток нужно сверять вручную.
- Для SMS действует капча и ограничение повторной отправки (30 секунд); после 5 неверных
  попыток номер блокируется на 5 минут. Это демо-защита, а не полноценный антифрод.
- В Android-сборке нет фоновых push-уведомлений и окна «Эфир».
- Прямая P2P-связь требует, чтобы приложение было открыто на обоих устройствах. Фоновой
  доставки и push нет; relay-события и комнаты живут в памяти и исчезают при перезапуске сервера
  или через 12 часов. Файлы в P2P ограничены 40 МБ, а их содержимое в истории доступно только до
  перезапуска приложения (метаданные сохраняются).
- P2P-история и очередь лежат в `localStorage` в открытом виде на устройстве; для защиты нужен
  пароль/шифрование диска. SAS-код нужно сверять вручную: signaling-сервер может попытаться
  подменить ECDH-ключи, но не может прочитать уже согласованный трафик.
- Бесплатный TURN по умолчанию не подключён. Если мобильный оператор блокирует и UDP, и
  WebSocket-relay, остаётся только офлайн-обмен SDP-кодами (он требует прямого ICE-соединения).
- UPnP/NAT-PMP — best-effort и не работает при CGNAT или выключенном UPnP на роутере.
- Нет звонков, push-уведомлений и управления группой после создания (переименование, добавление и
  удаление участников, аватар группы).
- Полноценного мультиустройства нет. «Войти с другого устройства» — это перенос: новый клиент
  получает копию E2EE-ключа, а старая сессия отзывается после завершения. Два независимых
  устройства с разными ключами и общей историей не поддерживаются.
- Перенос ключа работает, только если старое устройство открыто и онлайн (или откроется до
  истечения 5-минутного кода). Иначе можно войти без старой истории — старые complex-сообщения
  останутся недоступны.
- Для реальной эксплуатации включите HTTPS (обязательно), закройте регистрацию по инвайтам и
  ограничьте доступ к каталогу `data`.
